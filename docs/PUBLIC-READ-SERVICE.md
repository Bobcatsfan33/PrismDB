# Authenticated public API

`prismd serve` is PrismDB's supported HTTPS boundary. It is a
separate process from shard storage and accepts only mutual-TLS clients. The
normative API description is
[`openapi-public-read-v1.yaml`](openapi-public-read-v1.yaml).

## Identity and tenant authorization

TLS first validates that the client certificate chains to the configured
public-client CA. Application authorization then hashes the exact leaf DER
certificate with SHA-256 and looks it up in a bounded, versioned policy. A CA
valid certificate that is absent from policy receives `403`; CA membership is
not product authorization.

Each identity has an explicit tenant list, scope list, and in-flight limit.
Wildcards and duplicate grants are refused; a health/metrics-only identity may
have no tenants. `/v1/search` requires the `search` scope and injects the
requested tenant only after proving it is in that certificate's grant. The
public request cannot select cross-tenant search, `best_effort`, a physical
plan/route, or internal candidate/rerank tuning. A tenant-scoped shard failure
therefore fails the request instead of returning a plausible partial result.

`/v1/events` independently requires the `ingest` scope. The request names one
authorized tenant and carries 1–1,000 events; `tenant_id` and `observed_time`
are absent from the event schema and are injected only after certificate
authorization. A caller cannot route to another shard, select a WAL record,
claim a receive timestamp, or control source offsets. Unknown fields fail. The
owning shard must advertise a replicated-WAL write door over the internal mTLS
protocol; a read-only shard fails the request by name.

Writers should assign a stable `idempotency_key` to every event and reuse it
when retrying an outcome they did not receive. The key is scoped to the
authorized tenant: identical content is acknowledged as a reported duplicate,
while reusing the key with different content is refused rather than silently
rewriting history.

Generate the policy fingerprint from the leaf certificate:

```bash
openssl x509 -in reader.pem -outform DER | openssl dgst -sha256
```

The policy file must be a regular non-symlink no larger than 1 MiB. It supports
at most 1,024 identities and 1,024 tenants per identity. Private keys retain
the shard transport's regular-file, 4 MiB, and Unix mode `0640`-or-stricter
checks (group-read only; no group write/execute or other access). Rotation
requires an overlap policy containing both old and new leaf
fingerprints, a rolling restart, proof that clients moved, then removal of the
old fingerprint and CA where applicable.

## Bounded protocol

- HTTP/1.1 headers cap at 16 KiB and bodies at 256 KiB before allocation.
- Duplicate headers and `Transfer-Encoding` are refused to avoid ambiguous
  request framing. One request is served per TLS connection.
- Search text caps at 64 KiB, result `k` at 100, and an ingest batch at 1,000
  events. The complete HTTP body remains capped at 256 KiB. Unknown JSON
  fields fail. Event, tenant, trace/span, and idempotency identifiers have
  explicit byte caps; idempotency-key bytes count toward admission quota.
- Socket deadlines are mandatory and limited to 100 ms–60 s.
- The listener caps connections at 128, while every identity has its own
  1–64 in-flight request cap. Excess work receives a named `429` or is closed
  before a TLS worker is spawned.
- `X-Request-Id` is bounded safe ASCII or generated by the service. Audit logs
  include request ID, identity, route, and status. Successful writes additionally
  record tenant, outcome counts, and snapshot; failed reads/writes record the
  tenant and a named internal error. Event bodies, query text, attributes,
  idempotency keys, and certificate bytes are never logged.
- TLS responses send `close_notify`; strict clients do not have to accept
  truncation-ambiguous EOF.

## Health, readiness, and metrics

`/healthz`, `/readyz`, and `/metrics` still require an authorized certificate
and their corresponding `health` or `metrics` scope. Readiness rechecks every
shard over mTLS and validates protocol identity plus immutable store routing,
dimension, seed, and advertised write mode. If any policy identity has the
`ingest` scope, every shard must remain writable; a shard restarted through the
read-only constructor removes the API pod from readiness. The Helm chart uses a
dedicated health-only certificate through `prismd probe`; it does not weaken
the public listener with a plaintext probe port.

Prometheus output uses fixed metric names with no tenant, identity, path, or
request-ID labels:

- `prism_api_connections_total`
- `prism_api_connections_rejected_total`
- `prism_api_requests_total`
- `prism_api_searches_total`
- `prism_api_ingests_total`
- `prism_api_ingested_events_total`
- `prism_api_duplicate_events_total`
- `prism_api_dead_lettered_events_total`
- `prism_api_failures_total`
- `prism_api_unauthorized_total`
- `prism_api_rate_limited_total`
- `prism_api_in_flight`
- `prism_api_search_latency_seconds_total`
- `prism_api_ingest_latency_seconds_total`

Customer SRE must set workload-specific SLO/error-budget thresholds. At
minimum, page on readiness loss, sustained search failures, and rejected
connections; ticket on increasing unauthorized or rate-limited traffic.
Repository metrics do not establish a production latency SLO without a
representative long-running load result.

## Deployment

The Helm chart requires an immutable `sha256:` image digest, at least two
replicas, explicit ingress and shard selectors, and a non-empty contiguous
topology. It renders non-root UID/GID 65532, read-only filesystem, no
capabilities, RuntimeDefault seccomp, no service-account token, required
anti-affinity, rolling availability, PDB, and default-deny ingress/egress with
only selected API clients, selected shard pods, and cluster DNS allowed.

The four referenced Secrets are created outside Helm:

- server TLS: `tls.crt`, `tls.key`, public-client `ca.crt`;
- shard client TLS: `tls.crt`, `tls.key`, shard `ca.crt`;
- authorization policy: `policy.json`;
- probe TLS: `tls.crt`, `tls.key`, server `ca.crt`.

Secret rotation and policy changes require a rolling restart because the
service snapshots cryptographic configuration at startup. A production
controller should annotate the pod template with the external secret version
or explicitly run a controlled rollout. The chart intentionally does not
render private keys or policy into a release record.

## Remaining boundary

The public ingest door and its remote-durable pre-publication recovery path are
implemented. The database product decision remains blocked: already-published
hot parts have no supported backup/hydration workflow, per-tenant envelope
encryption/KMS lifecycle is absent, and customer-scale RPO/RTO,
independent-host scale/chaos, representative long-running SLO, and independent
penetration evidence do not exist.
